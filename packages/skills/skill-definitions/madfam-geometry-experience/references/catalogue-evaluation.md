# Jewellery catalogue evaluation

Use this workflow when growing a native geometry library. Count a canonical
`repository / slug` once; sizes, materials, modes, presets and repeated components
are not additional hyperobjects. A manifest census catches exact duplicates;
a human construction review still decides whether proposed families should merge.

Jewelry Studio's local 100-family catalogue has solid, FC flat-pattern and Pliego
sheet representations. Keep the owning native representation visible. A flat
cutting guide is not a draped necklace; a loose multi-body CAD layout is not a
solved articulated assembly. Material selection does not qualify wood grain,
casting, gem retention, spring action or a wearable attachment.

Bind each catalogue row to a full source commit, resolved parameters and owning
engine commit. Evaluate a default and a geometrically changed design through the
native runner. Check the exported STEP again after import: a valid source shape
can lose or separate bodies during an export path. Check all intended solids,
not just the first item on a CAD workplane stack. Keep expected body counts
explicitly enabled. A seam check with zero seams is only outline evidence.

The local application profile is `madfam.jewelry-catalogue-instance` 0.1.0-draft.
Its evidence index records exact coverage and the adapter/catalogue hashes.
Changing either invalidates displayed coverage until evaluation is renewed.
The skill's read-only checker supports that specific profile:

```sh
python3 <skill-dir>/scripts/verify-catalogue.py <jewelry-studio-directory>
```

It verifies 100 unique sources, both recorded parameter samples, request/document
and source digests, disclosed source bytes, positive native read counts, expected
bodies or seams, artifact hashes and exact ZIP contents. It never executes a
generator or recomputes geometry. Do not present this integrity pass as a new
native run, Linux CI, physical making, or independent commons acceptance.

The catalogue source commits are proposals; check their PR and merge status explicitly. New textile
labels retain human translation review as pending. Public inclusion, canonical
family consolidation and production pin advancement require their normal reviews.


## Independent construction review and Linux evidence

Watertightness is not a mechanism test. Review actual bores, connected channels,
shared hinge axes, insertion paths, rotational clearance and profile surfaces.
Cross-review a repair with a different reviewer and record the exact source hashes.
For textile subsets, verify dispatch and retained metadata through the native runner.
A printed loom guide is a reference guide, not textile stock. Seam-line area excludes
seam allowances, holes, layout waste and material consumption. Verify BOM CSV rows,
material roles and native BOM against the same instance, not merely their file hashes.

Keep local Linux execution distinct from a hosted CI run. Record OS, runtime package
versions, source and adapter hashes, exact coverage and the CI run URL when available.
Use separate environments for the keystone validator and the owning FC sandbox:
they can expose the same Python namespace at different revisions. A skipped native
CI job is no native evidence. Human translation and physical qualification remain
separate even after independent agent review and Linux execution pass.
