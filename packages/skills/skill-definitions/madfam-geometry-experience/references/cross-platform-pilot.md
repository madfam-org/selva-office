# Cross-platform pilot: test the consumer

Use this route when checking the local jewellery handoff. These are unmerged application
proposals in the owning platform repos; they do not ratify a new commons, shared schema or public
product. Check the local source evidence for base commits and exact proposed file hashes.

## Fashion Cabinet owns outfit placement

The consumer is `apps/web/studio/accessories.js`, with the local panel and dress-form point
projection alongside it. Its public-safe contract proposal is
`docs/spec/proposals/accessory-handoff.md`. It accepts the pilot's ring/braid private reference,
retains source pins/parameters and refuses mixed components with no shared frame.

The datum must be a current evaluated piece's declared landmark within its span. It is the
front of the body ring in Y-up mm, not a measured fastening point. Explicit offsets compose with
the source's Z-up→Y-up basis. The exported placement includes a dressing snapshot, garment
parameters, body, anchor and transform. A parameter/body/view change invalidates the placement.
No solid kernel or canonical jewellery generator moves into FC. The visual is a labelled point;
native jewellery geometry remains in the source editor. Without WebGL, use the numeric record.

Exercise both sides: download the source handoff; import into the loopback FC panel enabled by
`?accessories=local`; choose a real garment datum; inspect/export the matrix; reopen the exact
instance in the source editor; change garment parameters and verify stale export is disabled.
The source editor must actually load the saved instance. Merely checking the URL string is not
an editor round-trip. Also test unsupported mixed import, keyboard operation and phone/fallback.

Run FC's `node scripts/qa/accessory_handoff_check.mjs` and its native
`apps/api/tests/test_accessory_handoff.py` cases. Those render actual garments and feed the
result to the same JS consumer; the small JS fixture tests themselves are not native renders.
The local importer checks shapes, full pins and supported coordinates, not source authenticity.
Use the source bundle checker for byte/digest evidence. The garment snapshot is not a complete
immutable garment/runtime lock. Physical fit, fastening and collisions need further evidence.

## Blueprint owns discovery intake

The consumer is `services/ingestion/jewelry_plan.py`; the local CLI is
`scripts/plan_jewelry_discovery.py`, documented in `docs/JEWELRY_DISCOVERY_DRAFT.md`.
It is an offline plan adapter, not a registered live source connector. No catalogue/database,
fetch, upload or scheduler operation follows from generating a plan.

Use an unchanged private export first: it must be excluded before dependency metadata is
processed. Public-policy tests use explicit local test copies, never silently relabel a user's
design or publish it. Source hashes, complete pins and resolved component parameters are checked
independently. Shared component references do not make the authored assembly the same object.
An assembly needs its own declared licence; component licences are not inherited automatically.
Missing reviewed source policy stays disallowed. Current source evidence, approved allow-list and
an authorized target environment remain necessary for any later real ingestion.

Check repeated plans, a second design sharing a component, conflicting immutable ids and source
tampering. Withdrawal tombstones must block replay and release only unreferenced dependencies;
they do not revoke upstream licences. Existing persisted Yantra4D identities are not migrated by
this in-memory planner. Use `tests/unit/test_jewelry_plan.py` with the existing Yantra4D connector
tests to check this boundary. Do not report a local plan as an indexed, searchable public asset.

## What this adds to Anatomy

Anatomy's model-first SVG and illustration audits remain useful presentation tools. This pilot
adds source-native execution, explicit units/frames, quantities/export parity, a measured native
interface incompatibility, actual consumer reference placement and policy-aware discovery plans.
These are demonstrated task capabilities, not a universal quality ranking or a material solver.
For a broader superiority claim, compare equal tasks, source access, runtime and review criteria;
score correctness, useful explanation, valid export, handoff, accessibility and measured cost.
